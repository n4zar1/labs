El login sin clave

Medio · ~12 min · Basado en el vídeo «No sabía su contraseña. Escribí esto… y entré como administrador (inyección SQL)».

El caso. Tienda Sol, una tienda online ficticia (tienda-sol.example). Lunes 16/11. A las 10:50 alguien cambia los precios de toda la tienda a 0,01 € desde el panel de administración, y nadie del equipo ha sido. Te pasan el registro de accesos del servidor web, el registro del WAF y el código del login.

Tu misión: averigua quién entró como admin, qué escribió para hacerlo sin la contraseña, con qué herramienta siguió, por qué el WAF no lo paró y qué arreglo lo cierra. Chuleta: en una URL o un formulario, %27 es una comilla ', %3D es = y + es un espacio. En SQL, -- convierte en comentario todo lo que va detrás. Ojo: no toda comilla es un ataque.

1 · access.log del servidor web · 16/11 (la app apunta el campo «usuario» de cada intento)

2 · WAF (ModSecurity + OWASP CRS) · registro del 16/11

3 · La web por dentro: el login y la configuración del WAF

// login.php (PHP 8)
$u = $_POST['usuario'];
$c = hash('sha256', $_POST['clave']);
$sql = "SELECT id, rol FROM usuarios WHERE usuario = '$u' AND clave = '$c'";
$fila = $db->query($sql)->fetch();
if ($fila) { $_SESSION['rol'] = $fila['rol']; header('Location: /admin'); }   // 302
else { http_response_code(401); }

# modsecurity.conf
SecRuleEngine DetectionOnly   # puesto el 02/11 «para probar sin romper nada»

Reto completado

Bandera:

Lo que haría Tienda Sol: cambiar el login (y todas las consultas de la web) a consultas parametrizadas, WHERE usuario = ? AND clave = ?, para que lo que se escribe sea siempre texto (OWASP SQL Injection Prevention Cheat Sheet); volver a poner el WAF en SecRuleEngine On; cerrar las sesiones del panel, cambiar las contraseñas y restaurar los precios; bloquear 203.0.113.45 y revisar qué sacaron las consultas UNION, porque puede haber una filtración de datos de clientes que habría que notificar. Y nada de esto se prueba fuera de sistemas propios o sin permiso.
